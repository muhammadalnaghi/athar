# WM031: Parent-local review intake

## Goal

Identify which unsupported evidence families still require review before expanding automatic recording. Parser success, posting authority, optional categorization and independent financial correctness remain different claims. This is a gated JVM diagnostic only, not a transaction repair, production parser change, model-training export or device operation.

## Inputs and boundary

Use the already-authorized, untouched prepared received-message archive through the real built-in template registry. The existing explicit environment opt-in remains mandatory. Preserve original byte hashes and source identifiers. Do not expose message bodies, senders, monetary values, account identifiers or literal headers in generated reports. Other agents receive public source and synthetic fixtures only; they must never inspect this diagnostic's inputs or results.

## Outputs

Retain the existing failed-reference file and aggregate assertions. Add a parent-private success index containing stable source reference, matched public template ID, transaction type, posting state/support, whether a source-stated date exists, literal currency, coarse lexical shape tags and a SHA-256 first-line grouping token. Tags such as purchase, income or verification code are investigative hints, never new payment authority. The header token must not be treated as anonymization suitable for publication.

## Acceptance and exclusions

The diagnostic must actually execute, produce a fresh index whose unique row count matches the real successful parser population, and preserve the original input hash. Verify declared versus actual JUnit testcase counts and zero unexpected failure/error/skip. Aggregate the index deterministically; do not infer the pending population solely from parser evidence or equate missing categorization with financial ambiguity. Bind findings to current parser source. A match to a lexical tag cannot authorize auto-confirmation, suppress a record, change money, or establish that the complete archive is financially correct. Installed application artifacts and production rollout settings remain unchanged by this test-only work.
